# Owner Profile: authenticator app and passkeys
**Status:** 2026-11-23 — Implemented in the working tree and tested with disposable services. Review fixes are tracked in [2026-11-23-owner-mfa-review-fixes.md](2026-11-23-owner-mfa-review-fixes.md). Chromium e2e passes (247 passed, 2 skipped, 0 failed). Not deployed; the physical-device HTTPS smoke check, WebKit e2e and the real-Chromium profile fixture (needs a disposable `E2E_URL`) have not run and remain before release.

## Goal and scope
Give the existing single owner a private Profile page to see their sign-in email and secure their account without changing pipeline settings or creating another account.

**Sign-in choices:** The login page offers **Sign in with a passkey** alongside the password form, before any email or password entry. A registered, user-verified passkey signs the owner in directly, without a password or authenticator code. On the separate password path, enabling authenticator MFA requires a TOTP or unused recovery code after the password. Adding a passkey alone does not turn on MFA for the password path; explain this distinction in Profile. Editing account identity is out of scope.

## Baseline before implementation
- In `internal/api/server.go`, setup and login shared `handleAuth` and its session-issuance tail. Setup claims one owner; the bootstrap key is not an account-recovery mechanism. Both the API guard and public auth status checked only whether a Redis session exists.
- In `apps/web/src/main.tsx`, Login discarded the login response and refreshed queries. The shell opens only when auth status reports an authenticated session. Keep that gate; a password accepted for MFA is not a successful sign-in.

## Acceptance
| Scenario | Required result |
| --- | --- |
| Bootstrap and upgrade | Setup succeeds only for an unclaimed owner. An existing unenrolled owner can sign in with their password after the one-time session reset. |
| Password accepted; TOTP pending | Auth status remains anonymous; Profile, media, API docs and OAuth routes stay closed. Missing or mismatched browser binding, wrong origin/header, expired or exhausted attempts fail. Restarting an attempt does not reset the aggregate guess limit. |
| First TOTP enrollment | Abandoning setup leaves password login unchanged. Completing QR or manual setup activates exactly one working seed with recovery codes. Reusing the activation code or submitting the same time step twice cannot authorize another action. |
| Passkeys | From a signed-out browser with empty email and password fields, select **Sign in with a passkey** and complete device verification. The resulting session opens Profile without a password or TOTP, including when TOTP is enrolled. Wrong origin/RP, missing user verification, replay and removed credentials fail. Cancellation leaves existing credentials unchanged. |
| Login choices and fallback | With only a passkey enrolled, either the passkey or password works independently. With both methods enrolled, cancelling passkey login opens no session; choosing the password still requires TOTP or recovery. With no passkey enrolled, the login page does not disclose enrollment status. |
| Recovery and changes | Password plus an unused recovery code works once. Lost regeneration preview retains the old set; confirmed replacement invalidates it. A stale tab cannot remove a new factor, and a previously valid session or pending login cannot survive a revision change. Removing the last passkey leaves password MFA enforced if TOTP is enabled. Disabling TOTP leaves any registered passkeys usable. |
| Partial failure and concurrency | Two concurrent completions yield at most one session per attempt or one use per proof. Simulate Redis/Postgres failures and a factor change racing password login: no stale proof grants access and a failed update cannot leave half an enrollment. 2026-11-23 note: covered by `TestOwnerSecurityPostgresFailure`, `TestOwnerSecurityFactorChangeRace` and `TestOwnerSecuritySessionStoreFailureKeepsRecoveryCode` (review-fix plan). |
| Profile UX | Desktop and mobile users can find Profile, complete or cancel both enrollment flows with a keyboard, save recovery codes and sign back in. A bad code permits retry within limits; an expired challenge returns to the login choices. |
