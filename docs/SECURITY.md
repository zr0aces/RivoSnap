# Security and privacy

- The proxy-to-web connection on the published web port (`WEB_PORT`, default `8080`) uses plain HTTP. Allow access only from the proxy and trusted LAN clients; do not forward this port from the internet. Docker-published ports bypass ufw and firewalld rules, so for a same-host proxy set `WEB_PORT=127.0.0.1:8080`. Use the HTTPS hostname for passwords, the bootstrap key and authenticated media, even on the LAN.
- Claiming the single owner requires an out-of-band bootstrap key, a unique singleton database row and a password of at least 12 characters. Passwords use Argon2id. The login endpoint is rate limited per client address (8 attempts per 5 minutes), as is the LINE webhook. The client address comes from `X-Forwarded-For` via the bundled Nginx, trusted only from private or loopback peers; keep `WEB_PORT` off the internet, because a client that reaches it directly from a private address can choose its own rate-limit key. Use a password manager.
- Rate limits, including the per-client-address aggregate guess limit (8 per 5 minutes across restarted attempts), live in API process memory and reset when the API restarts. One API instance is the supported topology; running several instances requires moving these limiters to Redis first. An exhausted sign-in attempt, one that used its five wrong-code allowance, answers 429 and must start again.
- Residual risk in the recovery path: a client that disconnects after the server commits still uses up that recovery code or TOTP step. If the database commits but the client never receives the acknowledgement, the request fails closed, no session is granted, and the code is still used. Neither case can be closed without two-phase state; the owner keeps other recovery codes and passkeys.
- Opaque signed session cookies are HttpOnly, SameSite=Lax and Secure in production. Redis sessions expire after 12 hours. Logout invalidates the server session. Browser writes require the configured exact Origin and a custom request header; cross-origin CORS is not enabled. OAuth state is separate, short-lived, single-use and session-bound.
- Every image, thumbnail, configuration route and API document requires owner authentication. The webhook accepts no cookie authority: verify the HMAC of raw bytes. Public auth status exposes only setup and session flags. Readiness returns dependency availability without credentials.
- Access tokens, refresh tokens, LINE content and webhook bodies must never be logged. App request logging is disabled; safe failures include the route and error type only. Ensure external proxies and hosting dashboards also omit query strings and sensitive headers. Never enable provider HTTP tracing in production.
- TOKEN_ENCRYPTION_KEY is 32 random bytes encoded as 64 hex characters. AES-256-GCM protects TOTP seeds, the Google refresh token and saved LINE credentials with independent random nonces. Preserve the key separately when backing up; without the original key, those three secrets are unreadable after a restore. Changing it without re-encryption requires reconnecting Google, resaving LINE credentials and re-enrolling the authenticator. Changing SESSION_SECRET invalidates signed cookies.
- Non-root containers, isolated Redis/Postgres network, no browser mounts, service-generated UUID paths and private file modes restrict media access. Image decoders and ffprobe restrict decoded dimensions (100 MP limit); downloads have a byte limit and timeout. Only validated JPEG/PNG/WebP/GIF images and MP4/MOV/WebM videos (when `collectVideos` is enabled; off by default) are accepted. Google URLs are resolved from app-created IDs, not browser-supplied URLs.
- Do not enable a group until participants know personal images are copied to the owner's Google Photos account. A private group is not blanket consent. Pausing collection stops new ingestion; already accepted work finishes. Removing local credentials, cached files, or the deployment does not remove Google originals. The owner manages remote deletion outside this app.
- Provide a privacy notice and operator contact appropriate to the actual deployment. Use encrypted host disks and backups. The application does not provide end-to-end encryption from group participants to Google: LINE, the worker, the owner and Google handle image data.

## Owner authentication changes

- Owner MFA and passkeys first ship in the release after `2026.11.7`. `2026.11.7` and `latest` published before that release are password-only.
- Password verification with authenticator MFA enabled returns only a pending challenge. A passkey is a separate passwordless route: require a discoverable credential, a valid assertion and device user verification against the configured APP_URL origin and hostname. Keep the HTTPS hostname stable; changing the relying-party ID requires enrollment of new passkeys.
- Redis holds five-minute browser-bound ceremonies, separate from full sessions. Confirming a change checks the original session, target and owner security revision. Security changes advance that revision in Postgres and invalidate all existing sessions and pending proofs. Pre-upgrade sessions must sign in again.
- The TOTP seed (including pending enrollment) is encrypted with TOKEN_ENCRYPTION_KEY. Back up that key separately. Preserve independent passkeys or unused recovery codes in case the authenticator or encryption key is lost. Never log or externally render setup URIs, QR codes, recovery codes or credential proofs. Recovery codes are stored as hashes and consumed once.
- Upgrade the whole API before permitting enrollment. Do not mix or roll back to a binary that ignores MFA; take the API offline and forward-fix instead. The migration runner refuses an older binary against this database (`database has migrations unknown to this binary`), so a rollback fails closed. Never clear enrolled security state as part of a routine rollback.

## Resource limits

- Password hashing (setup, sign-in and profile password checks) runs two Argon2 operations at a time per process. A request that waits 5 seconds for a slot answers 503 with `Retry-After: 2` and "Sign-in is busy. Try again shortly."; wrong passwords still answer 401. Run one API instance.
- On-demand previews run `ffmpeg` only on originals that passed inspection. A quarantined or uninspected row gets no on-demand preview, and its thumbnail answers 404 when it has no Google copy.
